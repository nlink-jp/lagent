## Context（背景）

lagent のレーンの移植元である gem-agent ADR-0073 は、シェルのコマンド文字列から
Safe を導出する設計を領域の議論で撤回した。コマンド文字列は無限の領域、カーネルは
有限の領域であるから、判定はカーネルへ移り、文字列規則は判定を上げることしか
できない床としてのみ残る。残った 13 個の `blockPatterns` が許容できるのは、そこでの
見逃しのコストが「檻がいずれ捕まえる確認 1 回」だからである。

file ツールはその移動を、どちらのランタイムでもしていない。Seatbelt を通らない
からである。`os.Root` 経由で開くインプロセスの Go コードであり、`read_file .env`
とモデルの間に立つのは Go で書かれた照合器 `sandbox.CredentialPath` だけである。
そこでの見逃しは確認の欠落ではない。ファイルの内容が transcript に載り、そこから
モデルが何であれそこへ入ることである。

ADR-0015 はその照合器に第 2 の仕事 — 列挙ツールがどのエントリを差し止めるかの
判断 — を与えた。利用者の観察は、その仕事が増え続けているというものである。同じ
コードを持つ gem-agent の履歴がそれを平明に語る。レーンが入って以降、資格情報
一覧は 1 項目増えた一方、照合規則は 6 回変わり、うち 4 回は 1 リリースに集中し、
いずれも独立レビューの所見由来で、いずれも直前の規則が想定しなかった綴りだった。
lagent はこの曲線の先にいるのではない。後ろにいる。walk はいまだにプロジェクト
相対の綴りで判定し、根を解決していない。これは gem-agent の v0.78.0 のレビューが
見つけて塞いだ欠陥である。

理由は両者で同じである。**既知のファイルへのパスの綴り方の集合は無限である。**
ファイルの一覧は有限であり、そこは問題ではない。

### カーネルが実際に何をするか

2026-09-13 に計測。プロファイルは `(allow default)`・`(deny file-write*)`・
`(deny network*)` と資格情報 deny・`.env` テンプレート再許可だけを持つ:

| `.env` への操作 | 結果 |
|---|---|
| `cat .env` | `Operation not permitted` |
| `stat .env` | 許可 — deny は `file-read-data`。下記参照 |
| `cat .env.example` | 許可 — テンプレート再許可が効く |
| ディレクトリ全体の `grep -r` | その 1 ファイルだけ拒否して続行 |
| `ls -a` | **`.env` の名前は一覧に出る** |

カーネルは内容に対しては完全な境界であり、メタデータと名前に対しては境界では
ない。演算子の選択が効く: `file-read*` はメタデータも拒むが、Go の `os.Root` の
一覧は各エントリを stat するので、拒まれた名前が 1 つあるだけでディレクトリ
読取全体が失敗し、あらゆる walk が "no matches (0 files scanned)" を返した
（独立レビュー、実測。初版はその状態で出荷された）。`file-read-data` は内容を
拒み stat を残す。

同じ機体での起動コスト、各 10 回:

| 対象 | 1 回あたり |
|---|---|
| 素の `/usr/bin/true` | 1.8 ms |
| `sandbox-exec` + `/usr/bin/true` | 7.8 ms |
| `sandbox-exec` + このバイナリ | 18.8 ms |

file ツールのコールは既にモデル 1 往復を伴い、ローカルモデルではその往復は秒で
測る。19 ms は設計を曲げる予算ではない。

## Decision（決定）

### 1. モデルが求めた読取はサンドボックス下の子で起きる

レジストリの読取プリミティブは、専用プロファイルの `sandbox-exec` で包んだ子で
走る。ツールコール 1 回につき 1 回の起動、このバイナリを内部サブコマンドで再実行
し、要求は stdin に（argv は `ps` で誰にでも見える）、バイトは stdout に乗る。
どちらも上限付きである。

プロファイルは基本部に `(deny network*)` を足し、`sandbox.CredentialFilters(home)`
を `(deny file-read* …)` として置き、その後に `.env.example` 系を再許可する。他の
全ての強制者が読むのと同じ `internal/sandbox` の一覧から作る。

プロジェクトの封じ込めは Go に残す。カーネルはプロジェクトの場所を知らず、
`os.Root` は既に syscall で脱出を拒む（gem-agent ADR-0072 §4）。カーネルには 1 つ
だけ仕事を与える。**このプロセスでは資格情報を開けない。**

対象: `read_file`・`file_info`、および `search_files` の walk 全体。walk は子の
中で走らせ、そこで行う全ての open がカーネルの裁定を受けるようにする。
`view_image` は**コール**が対象である — ツール自体が子で走るので資格情報パスは
そこで拒まれる — 一方、モデルが受け取るバイトは添付経路がインプロセスで読み
直す。添付はコール自体が走ったときだけ走る。

### 2. 拒否が操作者への問いになり、照合器は境界であることをやめる

拒否された open は型付きのエラーを返す。エージェントがそれを ADR-0015 §1 が定めた
操作者専用の確認に変え、承認されたら読取を**インプロセスで**再発行する。operator
レーンの権限を file ツールに適用したものである。資格情報を読めるのは操作者だけで
あり、その操作者がいま読めと言ったからである。拒否された open はバイトを生まない
ので、ゲートの前にモデルへ届くものは無い。

`risk.credentialRead` は正しさのためには不要になる。よくある場合に子プロセス 1 回を
使わずに確認を出すためだけに残す。そこでの見逃しのコストは子プロセス 1 回と
回りくどい確認であって、漏洩ではない。gem-agent ADR-0073 がシェルレーンに与えた
性質を、file ツールにも与えるということである。

### 3. 名前は伏せない — ADR-0015 §2 を撤回する

カーネルは名前を出し、内容を拒む。ファイル名は秘密ではない。秘密は内容である。
ADR-0015 §2 は「`.env` を黙って隠す一覧は偽の『ここには無い』になる」と考え、
件数と最大 5 件の名前を報告することで答えた。gem-agent の ADR-0085 §2 は同じ前提
から逆向きに考え、名前無しの件数だけを報告した。どちらも残らない。内容が読めない
なら差し止めるものはもう無く、両ランタイムがエントリを他と同じく列挙し、読むこと
だけを拒む。

よって `list_files` と `list_tree` は資格情報のコードを一切持たず、
`credentialTally` は削除する。`search_files` は読めなかったファイルを名指して続行
する。`grep -r` が既に持つ形であり、gem-agent ADR-0052 が求める形である。

これは上に挙げた walk の欠陥も、塞ぐのではなく溶かす。open がカーネルの裁定を
受け、名前を判定しなくなるなら、walk が取り違える綴りはもう存在しない。

### 4. 天井は追いかけず、書き留める

この設計がしないことを 3 つ記録する。将来のレビューがこれらを「もう 1 つパターンを
足して塞ぐ穴」ではなく既知として報告するためである:

- **通常の名前を持つ資格情報ファイルへのハードリンク。** 正規化すべき実パスが
  存在しない。リンク自体が実名である。
- **通常の名前でのコピー。** 同じ。
- **一覧が名指さないファイルの中の秘密。** 内容検査はこの ADR が避けようとしている
  無限の領域であり、ADR-0015 が既に却下している。

ADR-0015 が「予定ではなく受容」として記録した残余 — read レーンが設定ファイルと
transcript を読めること — はこの ADR では変わらず、受容のままである。

### 5. 劣化はレーンと同じく計測する

起動時に、read レーンと同じ形で子を検証する。プロファイルが必ず拒むプローブ
ファイルと、必ず読める通常ファイル。失敗したら file ツールは
`risk.credentialRead` を境界とするインプロセス読取へ退避し、起動時の警告がそれを
名指す。カーネルが見張っていると主張する劣化状態は、照合器より
悪い。

*2026-09-13 修正（アーキテクチャ解説 第 2 改訂の作成時）: §5 の
「`risk.credentialRead` を境界とする」は、走査については元から真ではなかった。
あの関数が判定するのはパス**引数**であり、`search_files` は引数を持たない。
資格情報の読取ツール一覧に無く、判定は `Safe` で、ゲートに届かない。したがって
檻を据え付けられなかった機体では、走査が資格情報ファイルを開き、一致行を何も
挟まずにモデルへ印字していた。エントリを伏せて件数を報告していた前版より弱く、
しかも劣化時の注記は操作者に逆のことを告げていた。`readForSearch` は、ファイルを
開く前に同じ一覧でパスを拒むようにする。返すのは走査が既に扱い方を知っている
permission エラーであり、カーネルが拒んだ場合とこの検査が拒んだ場合とで、同じ
`[not read: …]` の脚注に載る。拒否は檻の不在で切り替えず**無条件**とする。モード
分岐は最も実行されない経路に安全性を置くことになり、それがまさに今回の出荷され方
だったからである。子プロセスの中ではこの検査が見逃したものをカーネルが引き続き
拒むため、ここでの一覧は速い経路であって境界ではない。§2 の性質は変わらない。
パスの綴り方についての規則は 1 つも増えていない。同じ 1 つの一覧を、走査が
ファイルを開く 1 か所で 1 回引くだけである（§6）。*

### 6. これが残す判定基準

**項目は安く、規則が兆候である。** `internal/sandbox` にパスを 1 つ足すのは機構が
設計どおり働いていることである。パスの比較方法に規則を 1 つ足すのは、判定が誤った
領域に居ることの signal である。規則変更が 3 回続いたら、それは 4 回目の修正を要する
照合器ではない。境界の場所が誤っている。

## Consequences（帰結）

- 資格情報の照合器は読取について荷重を担うことをやめる。残るのはプロファイルの
  生成、シェルの Block 床、write ツールの Block である。
- 削除されるもの: `credentialTally`、`list_files`・`list_tree`・`search_files` の
  資格情報分岐、そして ADR-0015 §2。
- 追加されるもの: プロファイル関数 1 つ、内部サブコマンド 1 つ、型付きエラー 1 つ、
  再試行分岐 1 つ、起動プローブ 1 つ。
- 対象コール 1 回あたり約 19 ms 増える。相手は秒で測るローカルモデルの往復である。
- `search_files` は強くなる。読めなかったファイルを「無かったこと」にせず報告する
  からである。
- **対象外: 書込。** 資格情報パスへの `write_file` は Go 側の Block のままである。
  書込は秘密を公開するのではなく破壊するものであり、全ての書込は既にゲートを通る。
  対称な手は取れるが、ここでは取らない。
- gem-agent は同じ決定を ADR-0086 として取る。2 つのランタイムは 1 つの設計のまま
  であり、それが ADR-0001 の眼目である。

## Alternatives considered（検討した代替案）

- **常駐ヘルパープロセス。** 却下: 1 コールあたり 19 ms を節約する代わりに、
  プロトコル、ライフサイクル、`/clear` の作業ディレクトリ回転と結合した再起動
  経路、そしてセッション途中でヘルパーが死ぬ新しい障害クラスを払う。
- **エージェントプロセス自身をサンドボックス化する。** 不可能: プロファイルは
  エージェントが正当に行うこと全部を許さねばならず、`sandbox_init` は不可逆かつ
  非推奨である。
- **プロジェクト封じ込めもカーネルで。** 却下: 子は自身の実行ファイルとシステム
  ライブラリを読む必要があるので、全体 read deny はシステム再許可の一覧に化ける。
  それは新しい無限の一覧である。`os.Root` は既に正しく封じ込めている。
- **照合器を境界のまま残し、カーネルを第 2 層として足す。** 却下: 1 つの規則に 2 つの
  境界は「一覧は 1 つ、強制者は N 人」が避けるためにある形であり、照合器が荷重を
  担い続ける。それが今回の指摘そのものである。
- **gem-agent v0.78.0 がしたように walk の根の解決を直す。** 出荷済みの設計に対して
  は正しく、この設計に取って代わられる。その修正が直すコードは、ここでは削除される。
