## Context（背景）

v0.4.0 はシステムリスクレビューの R01 に対し、read レーンの環境変数 scrub の中に
あった `LAGENT_` 接頭辞免除を 3 つの名前の一覧 `readLaneExports` に置き換えて
答えた。所見は実在した。接頭辞が免除されていると `LAGENT_API_KEY` が scrub を
生き延び、read レーンのコマンドに届く。そのコマンドの出力は無確認でモデルへ行く。

利用者の問いは、そもそも scrub が存在すべきかである。2 つの計測が、これは元から
制御ではなかったと言う。

**6 つの子のうち 1 つしか覆っていない。** 他の子はすべて操作者の環境を丸ごと
受け取る:

| 子 | 環境変数 |
|---|---|
| read レーンのシェル | scrub 済み |
| write レーンのシェル | 全部 |
| operator レーンのシェル | 全部 |
| `!` 直接シェル | 全部 |
| MCP サーバ | 全部（`cmd.Env = os.Environ()`、加えて設定自身の `env` ブロック） |
| フック | 全部（`cmd.Env` 未設定なので継承） |

**そしてその 1 つの扉も漏れる。** 出荷中の正規表現では次が素通りする:

```
OPENAI_KEY  GH_PAT  STRIPE_SK  ANTHROPIC_KEY  GPG_PASSPHRASE
SESSION_COOKIE  BEARER  LICENSE_KEY  PAT
```

`NPM_TOKEN` は捕まり `OPENAI_KEY` は捕まらない。システムリスクレビューも 10 章で
既に結論を書いていた。「秘密を環境変数に置けば一律に保護される、とは説明できない」。

### 許可リストが解にならない理由

分かりやすい修理 — 拒否リストを反転し、read レーンに必要なものだけを渡す — は
却下する。正当なツールチェインが読む変数の集合は、秘密が取り得る名前の集合と同じ
くらい open-ended である。`GOFLAGS`・`GOMODCACHE`・`GOPRIVATE`・`PYTHONPATH`・
`VIRTUAL_ENV`・`JAVA_HOME`・`CARGO_HOME`、そして来月出るツールがもう 1 つ。許可
リストは無限の一覧を「秘密らしい名前」から「何かが必要とする名前」へ移すだけで、
失敗を「静かな漏洩」から「一覧が追いつくまで read レーンのビルドが壊れる」へ
変える。それは ADR-0008 が取り除くために書かれた摩擦である。

つまり環境変数には、どちら側にも有限領域が無い。これが ADR-0016 との違いである。
あちらにはカーネルが実在し、判定がそこへ移る。こちらには無い。環境変数は親が
`exec` に渡すものが全てであり、それを濾す OS の機構は存在しない。判定を移すべき
有限領域が無いなら、規則は存在すべきでない。

### 何が有限か

1 つだけ有限で、列挙可能で、書いた本人が網羅的に知っている集合がある。**lagent
自身の名前空間の変数である。** `LAGENT_*` を読むのは他に誰もいない。今日の時点で、
完全に:

| 用途 | 変数 |
|---|---|
| ランタイムが自分のために読む | `LAGENT_STATE_DIR`・`LAGENT_PROVIDER`・`LAGENT_BASE_URL`・`LAGENT_MODEL`・`LAGENT_API_KEY`・`LAGENT_REASONING_EFFORT`・`LAGENT_LLM_TRACE`・`LAGENT_MCP_STDERR` |
| ランタイムが子のために export する | `LAGENT_WORK_DIR`・`LAGENT_PROJECT_DIR`・`LAGENT_SESSION_ID` |

`LAGENT_API_KEY` は左の列にある。R01 が名指した変数であり、下の規則によって、何も
`key` という語を認識することなく、全ての子から外れる。

元の接頭辞規則は、領域について誤ってはいなかった。反転していたのである。
`LAGENT_*` を**残し**、残り全部を推測していた。同じ領域の正しい読み方は、3 つの
export 以外の `LAGENT_*` を**外し**、他は何も推測しないことである。

## Decision（決定）

### 1. 操作者の環境変数には触れない

`sandbox.ScrubEnv`・`secretEnvRe`・`readLaneExports` を削除し、承認リファレンスの
read レーン行にある主張も併せて削除する。read レーンのコマンドは操作者が置いた
ままの環境を受け取る。そこで走るプログラムがどの変数を必要とするかは、この
ランタイムが答えられる問いではないからである。

### 2. ランタイム自身の変数はどの子にも渡らない

このランタイムが起こす子 — read・write・operator レーンのシェル、`!` シェル、
MCP サーバ、フック — は、親の環境から lagent 自身の設定変数を除いたものを受け取る。
3 つの export は今日どおり付加する。子のために存在するものだからである。

関数 1 つを全ての spawn 地点に適用する。子を足したときに規則を継がないことが
起きないようにするためである。

### 3. 分割はテストで閉じる。注意深さでは閉じない

非テストコードの `LAGENT_` 文字列リテラルは、2 つの一覧のどちらか一方にちょうど
1 回現れねばならない。新しい変数は、自分のものか相手のものかを分類するまでビルドを
失敗させる。

これが R01 の要求であり、構成によって到達する。`LAGENT_API_KEY` が子に届かなく
なるのは、それがランタイムの名前空間にあって export ではないからである。正規表現が
一致したからでも、誰かが秘密の一覧に足すのを覚えていたからでもない。

### 4. 真であることを 1 回だけ言う

lagent が起動された環境は、それが起こす全ての子に届く。文書は保護の主張の代わりに
それを言い、操作者が持つ対処を名指す。モデルに渡したくないものを持たないシェルから
起動するか、起動時にその変数を落とす。

## Consequences（帰結）

- read レーンの素の `env` は操作者の export した変数をモデルへ印字するようになる。
  write レーン・operator レーン・MCP サーバ・フックでは既にそうだった。read レーンが
  「規則があるかのように見せる例外」であることをやめる。
- 無限領域の規則が 1 つ消え、それを置き換えるものは無い。
- `LAGENT_API_KEY` は環境を通るどの経路でも子に届かなくなる。**設定ファイル経由の
  経路は閉じない**: この鍵は `.lagent.toml` にも在り、read レーンはそれを読める。
  ADR-0015 はその残余を、予定ではなく操作者が受容したものとして記録している。この
  ADR はそれを変えない。
- **シェルレーン内で入れ子に起動した `lagent` は、親の設定変数を継承しなくなる。**
  別に起動されたランタイムがそうすべきように、自分の設定ファイルを読む。子の
  ランタイム同一性はパラメータであって、継承した環境から推定するものではない。
- ambient な `LAGENT_*` を読んでいた MCP サーバは、MCP 設定の `env` ブロックから
  受け取る。サーバ自身の入力はそこに属する。
- bench のハーネスは自分が起動するランタイムに `LAGENT_STATE_DIR` を設定するが、
  これは影響を受けない。規則が支配するのは lagent が**自分で起こす**子に渡すもの
  であって、親が lagent に渡すものではない。
- gem-agent は同じ決定を ADR-0087 として取る。あちらのランタイム名前空間には今日
  秘密が無く、こちらにはレビューが見つけたその 1 つが在る。この規則が gem-agent
  より lagent にとって価値が高い理由はそこにある。

## Alternatives considered（検討した代替案）

- **拒否リストを維持し、足りない語を足す。** 却下: 利用者が名指した道そのもので
  あり、`OPENAI_KEY` がそれが終わらないことを示している。
- **read レーン用の許可リスト。** 却下: §Context のとおり、必要な集合は秘密の集合と
  同じく無限であり、失敗が仕事を壊す形で出る。
- **全ての子を scrub する。** 却下: 操作者が write・operator レーンから正当に動かす
  `gh`・`aws` 等を壊し、意図的に資格情報を与えられている MCP サーバも壊す。
- **`LAGENT_API_KEY` を環境から完全に外し、設定ファイルのみにする。** この問いへの
  解としては却下: 読める設定ファイルの中の鍵は同じ問題の別の装いであることを
  レビューが既に指摘し、ADR-0015 がその残余を明示的に受容している。この ADR は
  環境経由の経路を閉じ、そう述べるにとどめ、他方を閉じたとは主張しない。
- **何もせず、真実を文書化するだけ。** それが §1 と §4 であり、ADR 全体がそれで
  済んだ可能性はある。§2 を足したのは、有限な集合が 1 つ実在し、それを正しく扱う
  コストがゼロだからである。
