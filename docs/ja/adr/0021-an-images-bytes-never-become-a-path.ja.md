## Context（背景）

ADR-0020 はレーンを作り、供給源を開いたまま残し、反証された 3 稿すべてに対して成立した制約を
1 つ保持した。**view 層はファイルを開かない。** view 層が行う読み取りはツールコールではないので、
エージェントの判断にも ADR-0016 の sandbox 子にも届かず、ツール名で引かれるパス判定一覧 —
`pathJudgedTools`（[risk.go:323](../../../internal/risk/risk.go)）— からは見えない。

それが素直な設計を排除する。MCP intake は既に画像をセッションの work dir へ書き出し、モデルには
`[image saved at <path> … use view_image on that path]` を渡している
（[mcpresult.go:226](../../../cmd/mcpresult.go)）。つまりパスはそこにある。しかし `write` は
`os.Stat` で短絡し（[mcpresult.go:249](../../../cmd/mcpresult.go)）、毎回の呼び出しがサーバに
work dir を `_meta[workdir.MetaKey]` で渡す（[client.go:608](../../../internal/mcp/client.go)）。
ローカルのサーバ子は自分の名前・ツール名・返すバイト列・ディレクトリを知るので、応答の前に
content-addressed の名前へ symlink を置ける。するとランタイムは何も書かず、パスはサーバが選んだ
先を指す。`view_image` 経由でそこへ到達する道は封じ込められている。エージェントが強制者の判定
より先に symlink を解決するからである。パスを開く view 層はそうではない。

### こちら側の配管

反証された第 3 稿は、view 層に「intake が既に保持しているバイト列」を渡すと書いた。渡せない。
`render` は `string` を返し（[mcpresult.go:63](../../../cmd/mcpresult.go)）、`mcpIntake` が持つのは
work dir の getter とバイト上限とプレビュー長、そして本決定以降は sink であって（[mcpresult.go:56](../../../cmd/mcpresult.go)）、
一度も持ったことが無いのがバイト列であり、
ツール契約は `Run func(ctx, args) (string, error)` である
（[tools.go:67](../../../internal/tools/tools.go)）。

必要な経路はこちらにも既にあり、しかも同じものである。エージェントループはツールコールの
**最中に** UI へ話しかけている — `prog.Send(tui.ToolCall{…})`
（[root.go:819](../../../cmd/root.go)）。文字列契約は 1 ミリも動かさなくてよい。

### コスト

両ランタイムが共有するカウンタに対して gem-agent 側で測った（`physicalRows` は 2 つのツリーで
バイト同一である）: デコード後の画像 1 MiB あたり約 **3.6 ms**。64 KiB の 0.35 ms から 8 MiB の
29 ms まで線形で、payload の文字列は同時に 3 箇所に存在する — emit 経路、Bubble Tea のキュー、
端末の scrollback。今日これを縛るものは JSON-RPC のフレーム上限だけで
（`scannerMax = 10 MiB`、[client.go:29](../../../internal/mcp/client.go)）、ブロックあたりおよそ
7.5 MiB のデコード後バイト列を許す。測定をここで繰り返さないのは、それが測っているのが共有
コードであってランタイムではないからである。

## Decision（決定）

gem-agent ADR-0090 と同一である。intake もツール契約も UI 経路も、2 つのツリーで同じ機構だから
である。参照ではなく全文で述べる。この記録が単独で読めるように。

### 1. バイト列は帯域外を通る。UI が既に持っている経路で

`mcpIntake` は `workDir` の隣に任意の sink を 1 つ得て、ブロックを取り込む瞬間にデコード済み
バイト列と MIME 型で呼ばれ、`cmd` がそれを `prog.Send` に配線する。ツール結果は `string` の
ままで、transcript・resume・エラー経路には触れない。sink は対話的 TUI でない入口でも nil では
ない。以前の稿はそう約束したが順序が許さない — MCP サーバは UI の有無が決まる前に接続するので、
intake が受け取るのは未束縛の `tui.Screen` であり、束縛は後から、起きるなら起きる。未束縛の
それは不活性なので、one-shot `-p` と素の REPL は「描かないと判断する」のではなく渡された物を捨てる。

### 2. 画像を描くのは、intake が保存し記述したときに限る

注記が response budget に収まらないブロックは、既に保存も個別記述もされない — ガードは何かを
書く前に `binaryNote` の大きさを測る（[mcpresult.go:115](../../../cmd/mcpresult.go)）— そして
そうしたブロックは描かない。描けば、セッションの記録のどこにも現れない絵を操作者の画面に置く
ことになる。規則 1 つ、第 2 の budget ではない。

### 3. ボックスは絵から、切り詰めは端末から

`image.DecodeConfig` が絵をデコードせずにピクセル寸法を返す。行数はアスペクト比から天井に対して
決まり、列数は行数に従い、`termimg.Fit` が幅を端末より狭く切り詰める（ADR-0020 §2）。
`DecodeConfig` は検証器でもある。MIME が `image/*` と言ってもバイト列がデコードできないブロックは
画像ではなく、描かない。payload は base64 で、そのアルファベットに `ESC` も `BEL` も無いので、
view 層に届いたバイト列が包むエスケープから抜け出すことはできない。

### 4. デコード後 2 メガバイト

デコード後のバイト列が 2 MiB を超えるブロックは、通常どおり保存・記述され、描かれない。上限を
デコード後のバイト列に置くのは、実測コストがそれに比例するからであり、判定は payload を組む前に
行う。

### 5. モデルが見るものは何も変わらない

注記も、パスも、`view_image` の経路も、ADR-0005 が残したままである。モデルの到達路は依然として
強制者が判定を取るツールを通り、symlink は先に解決される。本決定が足すのは第 2 の観客 —
操作者 — であり、それにファイルを開かない経路を与える。

## Consequences（帰結）

- MCP サーバのスクリーンショットは撮られた時点で画面に出る。モデルは依然として自分で求める。
- symlink の事前設置は修理されず、悪化もしない。変わるのは、そのパスを新たに開くものが無い
  ことである。
- サーバが操作者の画面に絵を置けるようになる。もともと transcript にバイト列は置けたし、絵は
  このランタイムが宣言したボックスへ落ちるが、面としては新しいのでここで名指す。
- 2 MiB の天井はいくらかの画像を沈黙のうちに拒む。超過ブロックごとの警告は報告であって制御では
  なく、絵は `view_image` から到達可能なままである。
- **gem-agent に続いてこちらでも実装した。** レーンが向こうに先にあったためである。決定を
  両方の記録で同時に採ったのは、どちらのランタイムも単独でそれを持たないためであり、移植は
  gem-agent の実機初回実行が要求した消去（ADR-0020 決定 3）も併せて持ち込んでいる。

## Alternatives Considered（検討した代替案）

**A1. `Tool.Run` を構造化コンテンツを返す形に広げる。** 却下。文字列の結果は transcript が保存し、
resume が再生し、`RemoteError` が運ぶ — 4 つ目の都合で 3 つのサブシステムを変えることであり、
ADR-0020 §5 が 3 度反証された当の「数え上げられていない波及」である。

**A2. view 層が保存されたパスを読む。** 却下 — ADR-0020 §5 が獲得した制約であり、`os.Stat` の
短絡がそのパスをサーバの選べるものにしている。

**A3. budget に関わらず全ての image block を描く。** 却下。セッションの記録に含まれない絵を
画面に置くことになる。

**A4. バイトではなくピクセルで縛る。** 主たる上限としては却下。実測コストはバイトに比例する。
寸法は決定 3 のために読むので、証拠が出ればピクセル上限を後から足せる。

**A5. 画像を拒んだときに警告する。** 却下。超過ブロックごとの 1 行は報告であって制御ではなく、
操作者の次の行動は変わらない。

**A6. gem-agent の実装を待って移植する。** コードについては受け入れ、決定については却下する。
どちらが先に書くかは日程であり、片側だけが持つ決定は両ランタイムが過去に何度も修理してきた
非対称である。
