# ADR-0008: ランタイムは規則ではなく経路を供給する — ローカル向けプロンプト改訂

|-------|-------|

| Decision makers | nlink-jp maintainers |
| Triggered by | モデルが修正を散文で説明し、実行しなかったベンチ実行 — transcript は各段階にランタイム自身の手が入っていることを示した |

## Context

RFP の Phase 2 は「ローカル向けプロンプト改訂」を計測後に決めると書く。
ベンチ（ADR-0006）がその計測を供給した: `read-edit` の 8 回中 1 回で、
モデルは修正後のループをコードブロックで描写し、`edit_file` を呼ばずに
終わった。transcript を逆順に読むと、ランタイムが組み立てた連鎖である:

1. プロンプトは「変更後は検証せよ（shell_exec を access: write でテストか
   ビルド）」と言う。
2. モデルはまず read レーンで `go run .` を走らせた。失敗した: Go のビルド
   キャッシュは `~/Library/Caches/go-build` にあり、sandbox profile は
   プロジェクト・作業ディレクトリ・scratch の外への全書込を拒否する —
   両レーンとも、操作者の実機で（2026-09-12 にプローブ: read も write も
   同じ）。今日、sandbox 内でキャッシュが冷えた状態からビルドすることは
   不可能で、しかも write レーンの注記は operator レーンを指す — それも
   答えではない。
3. モデルは write レーンで再実行した。実行は `--auto` の one-shot で、write
   レーンのシェルは Review、尋ねる相手がいないので拒否された。拒否文は
   gem-agent のもの: 「代わりにユーザーにどう進めるか尋ねよ」。
4. one-shot にユーザーはいない。モデルは最も近いことをした: 行動をやめ、
   やるはずだったことを書いた。

全段階がランタイムの書いた一文に従っている。プロンプトは sandbox が走らせ
られない検証を求め、sandbox はタスクと無関係な理由でそれを失敗させ、ゲート
はエスカレーションを拒否し、拒否文は不在の誰かに相談せよと言った。修正は
「説明する前に編集せよ」という規則ではない — ナレッジベースは、常置の散文
規則がローカルモデルに何をするかを記録している（飛ばされ、禁止は第 3 の
経路を生む）。修正は、それらの文をそれぞれ真にすることである。

同じ transcript から小さなコストが 2 つ出た。全実行が `list_tree dirs_only=true`
で始まり、ファイル 2 つ・サブディレクトリ無しのディレクトリに対して
「(empty directory)」と言われ、`list_files` に 1 ラウンド費やして実態を知った。
そしてプロンプトのレーン段落は「ビルド・テストツールはキャッシュを書くので
write レーンが要る」と言う — それが真だったのは、ランタイムが他に書く場所を
与えていなかったからにすぎない。

## Decision

4 つの変更。それぞれ、モデルが従えない文を、従える事実に置き換える。
ベンチでまとめて計測する。

1. **ツールチェインのキャッシュは、操作者の持つ 1 つの表から、全レーンで
   セッション scratch に乗せる。** `[sandbox].scratch_caches` は環境変数を
   ディレクトリ名に対応付ける。全 `shell_exec` は各変数がセッションの private
   scratch（read レーンが書ける場所で、write と operator レーンも書ける）下の
   そのディレクトリを指す状態で走る。出荷する行は Go の `GOCACHE = "go-build"`。
   別のツールチェインを使う操作者はその行（`PIP_CACHE_DIR`、`UV_CACHE_DIR`、
   `npm_config_cache`）をコード変更なしに足し、空の値で行を消す。コンパイル・
   vet・テストは inspection と同じく read レーンで無承認で走り、キャッシュは
   セッションごとに 1 回冷え、以後は温かい。操作者の共有キャッシュを使わない
   のは意図的: read レーンは無承認で走り、共有の内容アドレスキャッシュは、
   無承認のコマンドが sandbox 外の後続ビルドが信じるオブジェクトを仕込める
   場所である。同じ縁はセッション内にもあるので、無承認のレーンと承認レーンは
   全行について別ディレクトリを持つ: read レーンは表の名前（`go-build`）、
   write と operator レーンは `<name>-approved` を共有する — 読んだもので
   誘導された read レーンのコマンドは、承認ビルドがリンクし操作者が実行する
   オブジェクトを仕込めない。表はその用途で有界: 行は再生成できるキャッシュ
   を名指さねばならず、レーンが決める変数（`TMPDIR`、`PATH`、`HOME`）と
   ローダ変数（`DYLD_*`、`LD_*`）は拒否され — read レーンが書くディレクトリが
   承認レーンの読み込むコードになってはならない — 値はパスではなく 1 つの
   ディレクトリ名。global 設定のみ: プロジェクトファイルは `[approval.tools]`
   と `[mcp].exclude` しか持たないので、クローンしたリポジトリは行を足せない。
   モジュール・レジストリのストア（`GOMODCACHE`、`CARGO_HOME`）はこの意味の
   キャッシュではなく、表には属さない。*（2026-09-12 同日改訂: 最初の版は
   Go だけのハードコード一覧だった。gem-agent ADR-0084 のレビューが表を
   操作者設定へ移しレーンのディレクトリを分けたので、本記録は両方を採る —
   ランタイムに機械のツールチェインを知る理由は無く、全行に適用する規則が
   ランタイムの持ち分である。）*
2. **無人の拒否は経路を名指す。** one-shot 実行ではエージェントは自分が無人
   だと知り（`Options.Unattended`）、拒否された呼び出しの結果はそう言う:
   この呼び出しを承認できる者はいない。承認なしで走るもの — 読み取り専用の
   ファイルツール、read レーンのシェル — で続けるか、終えて残りを述べよ。
   書き込みツールは名指さない: `--auto` や `--allow` が無ければそれこそが
   拒否されたもので、2 度目の拒否への経路はこの節が除く病理そのものである。
   対話時の文は「ユーザーに尋ねよ」のまま。
3. **`list_tree` は見たものを言う。** `dirs_only` で、ファイルはあるがサブ
   ディレクトリの無いディレクトリは、空と読ませる代わりにそのファイルを
   （ディレクトリごとの上限まで）列挙する。最初の版は件数と `list_files` への
   案内を返したが、実測ではモデルは毎回その案内に従い、ラウンドはやはり
   消費された — ツール自身が歩ける経路は名指す経路ではない。
4. **プロンプトは今真であることを言い、ランタイムが置き換えた規則を落とす。**
   レーン段落: read レーンは inspection *と* コンパイル・vet・テストを走らせる
   （ツールチェインのキャッシュはレーンの scratch にある。バイナリを
   プロジェクトに書くビルドは依然 write レーンを要する — プローブ: 単一
   main パッケージの `go build` がそれ）。write レーンはファイル変更、
   インストール、コミット、ネットワーク用。検証の箇条書きは
   read レーンを名指す。「拒否は決定であって障害ではない — どう進めるか
   尋ねよ」の箇条書きは消える: 拒否結果が経路を運ぶ。`write_file` の箇条書きは
   肯定形で 1 回。`shell_exec` 自身の説明も同じ文言に従う。

プロンプトの他は動かさない。セキュリティの枠は先頭のまま不変、プロンプトは
セッションをまたいでバイト同一のまま（ADR-0003）。

## Consequences

- ベンチで 3 反復、前 → 後を計測: この記録の日付で `reference/bench.md` に
  記録する。実行前に書いた期待効果: `read-edit` が 3/3 完了し検証が read
  レーンで成功する。全タスクが `list_tree` 後の `list_files` ラウンドを失う。
  拒否の後に散文で終わる実行が無い。
- sandbox 内の Go ビルドはセッションごと・信頼クラスごと（read レーンの
  キャッシュと承認レーンのキャッシュは別）に 1 回冷えた状態からコンパイル
  する。大きなプロジェクトではそれがビルドできることの代価で、操作者自身の
  キャッシュには触れない。キャッシュは作業ディレクトリと生死を共にし、
  占める容量の対処は `lagent workdirs clean`。
- scratch が無いとき（read レーン無効、またはディレクトリを作れなかった）は
  何も向け直されず、キャッシュは `~/Library` 下のまま全レーンで書けない —
  本記録より前の状態であって、新しい状態ではない。
- モジュールのダウンロードは対象外: `~/go/pkg/mod` はどのレーンでも読めるが
  書けないので、モジュールが未キャッシュのプロジェクトは実行内から取得
  できない。ここでは解かず、欠落として記録する。
- gem-agent の profile も同じキャッシュ失敗を持つ（同じ機械でプローブ）。
  移植元への提案は操作者の方針どおり保留し、この記録がその証拠になる。

## Alternatives considered

- **説明の前に編集せよ、one-shot では尋ねずに行動せよ、とモデルに言う。**
  却下: ランタイム自身が誘発した挙動に対する常置の散文規則で、ナレッジベース
  が計測した結果は「飛ばされるか過剰一般化する」である。
- **レーンで `~/Library/Caches` への書込を許す。** read レーンでは却下
  （無承認のコマンドが共有の内容アドレスキャッシュに書くのは汚染経路）、
  したがって write レーンでも却下 — 要点は read レーンでビルドが動くこと
  であり、両レーンで 1 つのキャッシュ位置ならセッション中は温かいまま。
- **ハードコードの一覧、ツールチェイン 1 つにつきコード変更 1 回。** 最初の
  版。同日に置き換えた（gem-agent ADR-0084 のレビュー）: ランタイムに機械の
  ツールチェインを知る理由は無く、追加のたびにリリースを要した。表は操作者
  のもので、ランタイムは全行に適用する規則を持つ。
- **全レーンで 1 つのキャッシュディレクトリ。** 同じレビューで却下: Go は
  キャッシュ項目を読み取り時に信じるので、無承認レーンが承認ビルドの消費する
  オブジェクトを仕込める。ディレクトリ 2 つの代価はセッションごとの冷えた
  コンパイル 1 回分。
- **one-shot で write レーンのビルドを自動承認する。** 却下: write レーンは
  ネットワークとプロジェクトに届く。「ビルド」はコマンド行の単語であって
  レーンではなく、規則層はコマンド文から意図を読まない（gem-agent
  ADR-0073）。
- **代わりに `list_files` を最初のツールにする。** 却下: プロンプトの案内は
  正しく、ツールの報告が偽だった。
