## Context

lagent はプロジェクトごとに保つものを、すべてプロジェクトのパスの文字列で
引いている: transcript の `project` フィールド（再開と `lagent sessions` が
これで絞り込む）、状態ディレクトリの `.project` 印、`policy.toml` の
`[projects."<path>"]` 表 — 信頼、内容の固定、プロジェクトごとのツールと
コマンドの許可リスト。

その文字列は `os.Getwd` から来ており、`os.Getwd` は `$PWD` が現在の
ディレクトリを指していれば `$PWD` を返す。濁点を含む日本語のパスには 2 つの
Unicode の綴りがある: 合成済み（NFC、入力メソッドが打つもの）と分解済み（NFD、
このクラウドストレージがディスク上に作ったもの）。macOS はどちらも同じ名前として
扱う。APFS 上で、それぞれの綴りで作った使い捨てのディレクトリに、それぞれの綴りで
入って測った:

| | NFC で入った | NFD で入った |
|---|---|---|
| `stat` | 見つかる | 見つかる |
| `os.Getwd`（`$PWD` に従う） | NFC | NFD |
| `syscall.Getwd`（カーネル） | ディスク上の綴り | ディスク上の綴り |
| `filepath.EvalSymlinks` | 与えた綴りのまま | 与えた綴りのまま |
| もう一方の綴りで書いた Seatbelt の `subpath` 規則 | 一致する | 一致する |

つまり同じディレクトリが、運用者のシェルがどう辿り着いたかによって 2 つの
プロジェクト文字列になった。失敗したセッションの記録は NFD（121 バイト）で、
後から NFC で打った `cd` は 115 バイトになった:

- `--resume` が拒否した: 「session … belongs to <path>, not <path>」。
- 状態ディレクトリの印が、2 つ目の綴りをパスのエスケープの衝突として拒否し、
  セッションは作業ディレクトリなしで走った。
- 一方の綴りで記録した信頼・固定・許可リストは、もう一方では見つからない:
  プロジェクトは信頼を再び尋ね、運用者の以前の判断は黙って消える。

サンドボックスは影響を受けない: Seatbelt は綴りをまたいで一致する。

## Decision

1. **プロジェクトのパスはカーネルから取る。** 現在のプロジェクトを決める
   コマンド（`lagent`、`sessions`、`trust`、`workdirs`）はすべて、作業
   ディレクトリを `$PWD` ではなくカーネル（`syscall.Getwd`）から取り、これまで
   どおりシンボリックリンクを解決する。綴りはディスク上のものなので、シェルが
   どう辿り着いても同じになる。アーキテクチャテストはモジュールのコードの
   どこでも `os.Getwd` を拒否するので、`$PWD` を持ち込む 2 つ目の読み手は現れない。

2. **パスは 1 つの関数で、ボリュームが名前を扱うのと同じ意味で比べる。**
   2 つのパスの比較 — 記録されたプロジェクトと現在のもの（再開と一覧のための
   transcript の `project`、状態ディレクトリの印、`policy.toml` のプロジェクトの表、
   `[approval].trusted_projects`）、そしてすべての包含判定（このパスはプロジェクト、
   作業ディレクトリ、スキル、保護されたディレクトリの中か）とそこからの相対パス —
   はすべて `internal/pathid` を通る: 両側を整え、Unicode の NFC に正規化してから
   比べる。文字列だけの純粋な関数である。6 つのパッケージが生の前方一致の判定を
   それぞれ持っていたが、今は `pathid.Within` を呼び、アーキテクチャテストはそれ以外の
   場所での生の `HasPrefix(p, base+separator)` を拒否する。この変更より前に
   どちらの綴りで書かれた記録も見つかり、ディスク上の何も書き換えない。

3. **大文字小文字は畳まない。** 大文字小文字を区別するボリュームでは、大文字小文字
   だけが違う 2 つの名前は 2 つのディレクトリであり、畳むと一方の信頼と許可リストが
   もう一方へ渡る。Unicode の形は違う: APFS と HFS+ は、それだけが違う 2 つの名前を
   決して持たない。

4. **書き込みはすでにある項目へ行く。** 現在のプロジェクトについての
   `policy.toml` の変更は — 消去も含めて — 綴りがどうであれ、すでにこの
   ディレクトリを名指している表に入るので、1 つのディレクトリが 2 つの表を持つ
   ことはない。

## Consequences

- 再開、状態ディレクトリ、信頼（記録されたものも設定されたものも）、許可リスト、
  包含判定は、パスがどう打たれ補完されても 1 つのディレクトリについて一致する —
  モデルや運用者がもう一方の形で打った絶対パスも含めて。
- 比較はディスクに触れない: 応答しなくなったボリュームで止まることはなく、その後
  別のディレクトリへのシンボリックリンクになった記録済みのパスを辿ることもない。
- `golang.org/x/text` は間接の依存から直接の依存になる（Go プロジェクト自身の
  モジュールで、すでにビルドに含まれている）。
- 扱わないもの（受け入れる）:
  - **この変更より前に書かれた 2 つの表**、綴りごとに 1 つ（もう一方の綴りで信頼の
    問いに答え直した運用者）: 現在の綴りと完全に同じものがあればそれを、なければ
    並べた順で最初のものを使い、もう一方は統合しない。そこにあったものは再び
    尋ねられる — 失敗は許す側ではなく尋ねる側に倒れる。
  - **記録とカーネルの綴りの、大文字小文字だけの違い**（大文字小文字を区別しない
    ボリュームで、違う大文字小文字で打った `cd` からできた古い記録）は一致しない。
    プロジェクトは再び尋ねる。
  - **firmlink の綴り（`/System/Volumes/Data/...`）でできた記録**は、カーネルの
    `/Users/...` とは別の状態ディレクトリ名にエスケープされる。そのメモリと作業
    ディレクトリは空から始まる。id による再開はこれまでどおり動く。

## Alternatives considered

- **ファイルの同一性（`os.SameFile`）で照合する。** 最初に実装し、リリース前に
  置き換えた: 両方のパスが存在する必要があり、包含判定に答えられず、ホットパスで
  記録済みのプロジェクトを stat し（応答しないネットワークボリュームが書き込みの
  たびに止まる）、その後シンボリックリンクになった記録済みのパスを辿るので、
  リンク先が記録の信頼を引き継いだ（リリース前レビュー）。
- **大文字小文字も畳む。** 却下（§3）。
- **読み込み時に既存の記録をカーネルの綴りへ書き換える。** 却下: 読み取りの
  問題を直すために運用者のファイルを書き換えることになり、transcript は起きたことの
  記録である。
- **カーネルの綴りだけにし、正規化した比較をしない。** 却下: `$PWD` の綴りで
  すでに書かれた記録が、更新後に一致しなくなり — 信頼は再び尋ねられ、許可リストは
  消え、セッションは再開できない — 打った絶対パスはプロジェクトの外になる。
