## Context

ADR-0004 は、モデルがサーバを読み込んだ時点でそのツールを広告する。ツールの塊が増え、次の要求は最初に変わった
バイトから処理し直しになる。チャットテンプレートはツールの塊を会話より前に描くので、その最初に変わったバイトは
セッションのすべてのメッセージより前にある。

基準機での計測（LM Studio、Gemma 4 26B A4B QAT、M2 Max。`LAGENT_LLM_TRACE` で取った実際の lagent の要求を使い、
会話は `read_file` の往復で水増し。読み込み直後の要求の最初のトークンまでの秒数。2 回の差は 5% 以内）:

| 読み込み前の会話 | github・ツール一覧（以前にキャッシュ済み / 空） | github・会話 | tor-exit-lookup・ツール一覧 | tor-exit-lookup・会話 |
|---|---|---|---|---|
| 1.3 万トークン | 11 / 41 | 36 | 8〜10 | 2.6 |
| 2.4 万トークン | 33 / 65 | 40 | 27〜31 | 3.3 |
| 4.7 万トークン | 85〜90 / 120 | 47 | 73〜82 | 3.2 |

github は 44 ツールでスキーマは約 1.75 万トークン、tor-exit-lookup は 4 ツールで約 1 千トークン。ツール一覧へ
読み込むコストは、サーバの大きさにかかわらずほぼ会話全体になる。4.7 万トークンの会話では、1 キロバイトの
スキーマのために 73〜82 秒待つ。スキーマを読み込みの結果に入れるコストは、会話の長さにかかわらずほぼスキーマの
分になる。ツール一覧が勝つのは、セッションの始めで、しかも同じサーバの塊が以前のセッションからサーバの
キャッシュに残っているときだけ。

ADR-0004 は代理を「ローカルモデルの引数の規律こそ、テンプレートを最も必要とする部分」として退けた。
それが未解決の問いで、試しの 1 回が既にそこを指している。github のスキーマを文として与えたところ、Gemma は
代理を通して `list_issues` を `query`・`sort`・`order` 付きで呼んだ — これは `search_issues` の引数である。
1 例では何も決まらない。

もう 1 回の試しで代替案が 1 つ閉じた。スキーマを会話に置き、代理を宣言しなかったところ、モデルは宣言されて
いないツールを名前で呼ばず、宣言済みの別のサーバを選んだ。モデルは、ツール一覧が差し出すものを呼ぶ。

## Decision

`[mcp].load_into` で、モデルの `mcp_load` がサーバのスキーマをどこに置くかを選ぶ: `"tool_list"`（既定。
ADR-0004 のまま、バイト単位で変えない）または `"conversation"`。`advertise = "all"` との組み合わせは設定エラー —
そこでは何も読み込まない。設定できるのは運用者の設定ファイルだけで、プロジェクトの `.lagent.toml` からは
設定できない。

`"conversation"` では:

1. **モデルの読み込みはツールの塊を変えない。** 塊にあるのは組み込みツール、`mcp_load`、組み込みの `mcp_call`
   1 つ、そして事前読み込みのサーバ（`[mcp].preload`、`--allow mcp__<server>__*`）。事前読み込みのサーバは
   ネイティブのまま — 最初の要求から塊にある。運用者自身の操作は今どおり塊を変える: `/mcp load`（運用者が
   選んだ時点でのネイティブな読み込み）、`/mcp reload`、設定パネルでの除外。
2. **宣言と呼び出し可否は別の判定。** ツールが宣言されるのは、そのサーバが事前読み込みかネイティブに読み込まれた
   とき。呼べるのは、どちらかの形で読み込まれたとき。読み込まれていないサーバのツールへの呼び出しを断る
   ADR-0004 の関門は「呼べるか」を見る。読み込み済みのツールを自身の名前で呼んだ場合（スキーマを読んだモデルは
   そうしうる）は、`mcp_call` で呼んだのと同じく実行する。
3. **`mcp_load` がスキーマを返す。** 結果は各ツールの完全な名前、レジストリが持つ説明（ネイティブの宣言が運ぶのと
   同じ文）、引数のスキーマ（JSON）を並べ、それらを `mcp_call` で呼ぶよう伝える。他のツール結果と同じく包まれ、
   `read_file` と同じく 200 KB で上限を切る。上限を超えるサーバは代わりにネイティブに読み込み、結果がそう伝える。
   この形で既に読み込んだサーバの再読み込みは何も出し直さず、前回の結果を指す。
4. **`mcp_call(tool, arguments)` は、ほかの何かが呼び出しを見る前にほどかれる。** エージェントは呼び出しごとの
   ループの冒頭で、それを指定された呼び出し — `arguments` 付きの `mcp__<server>__<tool>` — に変える。表示、
   ループ検出、pre-tool フック、判定の段、承認の確認、`[approval.tools]` のパターン、読み取り専用の上限、記録は
   すべて、ネイティブの呼び出しと同じく本物のツールを見る。`mcp_call_unwrapped` の記録が呼び出し id と中の
   名前を結ぶ。アシスタントのメッセージにはモデル自身の `mcp_call` が残り、結果は id でそれと対になり、中の
   ツールの名前を持つ。
   - `tool` は接続中の MCP サーバのツールを名指さなければならない。組み込みツール、`mcp_load`、`mcp_call` 自身は、
     直接呼ぶ道筋を添えて断る。読み込まれていないサーバのツールには ADR-0004 の道筋を返す（`mcp_call` も名指す）。
   - `arguments` はオブジェクトでなければならない。文字列にエンコードされたオブジェクトは復号する。それ以外は、
     期待する形を名指して断る。
   - `mcp_call` のスキーマは `lagent_purpose` を宣言する。ほどく処理がそれを中の呼び出しへ移すのは、lagent が
     中のツールにその引数を足した場合だけ（除去・表示・ループの署名が使うのと同じ「lagent が足したか」の条件 —
     ADR-0012 §5）。自分で宣言したサーバはそれを保つ。lagent が目的を除去するツールの集合は、宣言済みのツール
     だけでなく、登録されたすべてのツールについて計算する。呼べるが宣言されていないツールにそれが届くことはない。
   - `mcp_call` 自身の Run は常に断る — ほどく処理を飛ばした経路がサーバに届くことはない。
5. **モデルが読む文は、このレーンがすることを言う。** system プロンプトの MCP の節、`mcp_load` の説明、その結果、
   目録の見出し、読み込まれていないときの拒否文は、それぞれ `"conversation"` 用の文面を持つ。`"tool_list"` では
   どれも変わらない。system プロンプトは、1 つの設定のセッション間でバイト単位で同一のまま。
6. **再開**では、トランスクリプトの読み込みを、対になる結果がスキーマを持つときだけこの形の読み込み済みとする。
   持たない読み込み（`"tool_list"` で行われた、断られた、中断された）はネイティブに読み込むので、モデルは呼ぶ
   ツールのスキーマを必ず持つ。`"conversation"` のトランスクリプトを `"tool_list"` で再開すると、`mcp_call` の
   ターンは履歴として残る。そこでは `mcp_call` は登録されず、サーバはネイティブに再広告される。
7. **再接続はこの形の読み込みを忘れる。** `/mcp reload` やパネルからの再接続の後は、履歴のスキーマが古いかも
   しれないので、この形で読み込んだサーバは読み込まれていない状態に戻る。モデルは読み込み直す。

gem-agent は変えない。そちらのツールの塊は、プロバイダ側のキャッシュの後ろで課金される入力トークンであり、
ローカルの prefill の秒数ではなく、何も測っていない。計測が求めれば、この仕組みは移植できる。

## Acceptance

2 層で測る。エージェントの実行で示せるのは、経路が働くことと実行全体のコストまでで、3 回の実行では率は
運べない（ADR-0018 §5）。

**実行全体** — ベンチ（ADR-0006）で、`baseline`（`tool_list`）と、同じ設定に `load_into = "conversation"` を
足したものを、`mcp-load` スイートでタスクごとに 3 回。引数の規律のために作った試験サーバを使う（複数のツール。
スキーマには必須と任意の項目、列挙値、整数、配列、入れ子のオブジェクト、日付が混ざる。厳密に検証する。正しい
引数でしか答えに届かない）。実行ごとに数えるもの: 完了、試験サーバの引数の拒否、ランタイムの呼び出しの拒否
（未知または未読み込みのツール、形の崩れた `mcp_call`）、壁時計時間。

**最初の呼び出しの正確さ** — タスクとレーンごとに、読み込み直後の要求（それらの実行のトレースから）を取った
まま 30 回再送し、最初の呼び出しを試験サーバで採点する: 正しいツール、引数が受理される、答えに届く引数。

- **採用**: 会話レーンの最初の呼び出しの正確さが、どのタスクでもツール一覧の 10 ポイント以内で、全体では
  下回らず、実行全体の完了が同じだけあり（タスクごとに差は 1 回以内）、遅い読み込みのタスクで待ち時間の得が
  実行全体でも出ること。
- **却下**: それ以外。その場合この記録は Rejected として測った理由のまま残り、ADR-0004 の代替案は閉じる。

## Consequences

- 読み込み後の処理し直しは、セッションの大きさではなく、サーバのスキーマの大きさになる。大きなサーバ（github）は
  スキーマの分を 1 回は払う。
- `"conversation"` では組み込みツールが 1 つ（`mcp_call`）増える。セッション中は一定。
- サーバのツールの説明は、描かれたツールの塊ではなく、nonce で包まれたツール結果の中に届く — サーバの出力の
  残りが受けている、信用しないデータとしての扱い。残る危険（ここでは測らない）: サーバが説明に書く指示
  （「先に X を呼べ」）が、system プロンプトの「指示ではない」の規則の下に入る。
- 残る危険（ADR-0004 と共通）: 読み込みの印は `mcp_load` の Run の中で付くので、取り消しの床で放棄された
  読み込みも読み込み済みと数える。`"conversation"` ではそのスキーマが欠け、モデルの次の `mcp_load` は
  スキーマではなく前回を指す一文を返す。まれで、`/mcp reload` を促せば戻る。
- §Acceptance が別のことを言うまで、既定は `"tool_list"` のまま。運用者の設定の意味は何も変わらない。

## Alternatives considered

- **会話の中でしか見ていないツールをネイティブに呼ぶ**（代理なし）— 試した: モデルは宣言済みのツールを代わりに
  呼んだ。却下。
- **読み込んだサーバをツールの塊の末尾に足す** — ツールの塊は依然として会話より前にあるので、会話全体は依然と
  して処理し直しになる。差し込み位置より後ろの数ツールの分しか減らない。却下。
- **変わった接頭辞をまたいだサーバ側のキャッシュ再利用**（llama.cpp の `--cache-reuse` はキャッシュの塊を
  ずらして使う）— 全体を処理し直すことの近似で、lagent ではなくサーバの性質であり、LM Studio で使えるかは
  確かめていない。追わない。
- **2 段構え: 読み込みでは 1 行の一覧、求めに応じて 1 ツールのスキーマ** — 大きなサーバのコストはさらに減る。
  新しいツールごとに 1 往復増える。この記録の計測が出るまで保留。

## Review

実装の前に、独立した設計レビュー（2026-10-02）が 17 点を挙げた。決定に取り込んだもの: 目的の引数の除去と
移動（§4）、モデルが読む文（§5）、判定の分離（§2）、対になる結果による再開（§6）、ほどく先の限定と断る Run
（§4）、読み込み結果の上限と再読み込みの指し示し（§3）、再接続で読み込みを忘れること（§7）、名前を結ぶ記録
（§4）、設定の組み合わせ（Decision）、3 回の実行ではなく呼び出しごとの率（§Acceptance）、gem-agent についての
記述。残る危険として残したもの: 包みの中のサーバの指示、Run の中で付く読み込みの印（§Consequences）。

## Measurement（2026-10-02）

試作 `21d0b80`、LM Studio、Gemma 4 26B A4B QAT、M2 Max。

**実行全体**（`mcp-load` スイート、タスク・レーンごとに 3 回）: 両レーンとも 18/18 完了。引数の拒否も、
ランタイムの呼び出し拒否もなかった。ほとんどのタスクは同じ時間（1 回 17〜22 秒）だった。読み込みが
34 KB を読んだ後に来る `mcp-tk-late` では、中央値が 87 秒から 62 秒に下がった。

**試験サーバでの最初の呼び出しの正確さ**（読み込み直後の要求を取ったまま 30 回再送）: 両レーンとも 180/180。
**この層は差を見分けられなかった**: サーバ既定のサンプリングでは 12 セル中 8 セルが同じ呼び出しを 30 回出し、
試験サーバの依頼文は引数をはっきり名指している。

**本物のサーバでの追加確認** — 上の層が見えていなかったので足した: 記録した `mcp_load github` の要求
（44 ツール）、依頼文 6 種、それぞれ温度 1.0 で 20 標本。会話レーンにはそのレーンの文面（§5）を送った。
最初の呼び出しは、GitHub に接続せず、記録したスキーマに照らして採点した: 未知のキー、必須の欠け、列挙値、型。

| 依頼文 | ツール一覧 | 会話 | 会話レーンの外れ |
|---|---|---|---|
| 直近の open issue 3 件 | 16/20 | 厳密 0/20、`search_issues` を認めれば 10/20 | `search_issues` 15 回（うち有効 10）、`query`/`sort` 付きの `list_issues` 5 回 |
| "timeout" で issue を検索 | 17/20 | 20/20 | — |
| main の README | 20/20 | 19/20 | `pullNumber` 1 回 |
| open の PR を新しい順に | 11/20 | 厳密 6/20、`search_pull_requests` を認めれば 16/20 | `search_pull_requests` 11 回（うち有効 10） |
| 自分は誰か | 20/20 | 19/20 | ツール名のない呼び出し 1 回 |
| main の直近 5 コミット | 20/20 | 16/20 | `query` 付きの `list_commits` 4 回 |
| **合計** | **104/120** | **厳密 80/120、寛容 100/120** | |

スキーマを文として与えると、モデルは兄弟のツール（`list_*` と `search_*`）の間で引数を取り違える。これは
ADR-0004 が予言した失敗である。試験サーバの、はっきり名前の違うツールでは現れない。§Acceptance に照らすと、
追加確認は 2 つの依頼文（30 ポイントと 20 ポイント）と全体で基準を満たさない。本物のサーバは未知のキーを黙って
無視する: `query` 付きの `list_commits` は、絞り込まれないまま動く。

## Outcome

§Acceptance により却下。キャッシュの得は本物で、引数の規律の損も本物である。本物のサーバの兄弟ツールでの損は、
エラーにならずに誤って動く呼び出しで、待つことより悪い。ADR-0004 の代理の代替案は計測によって閉じる。2 段構えの
案は追わない: それでもモデルはスキーマを文として受け取る。

この作業から残すもの:

- ベンチの `tickets` 試験サーバの役と `mcp-load` スイート。厳密な MCP スキーマが正しく呼ばれるかの確認として
  残す。引数の規律の差を見分ける道具ではない: レーンの差を分けなかった。
- ランナーの `arg_errors` 列。
- スイートの実行のトレースを、その実行の隣に置く修正。

レーン自体 — `[mcp].load_into`、`mcp_call`、エージェントのほどく処理 — はランタイムに入れない。
