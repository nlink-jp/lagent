# ADR-0007: 空の completion は再送する、多くて 2 回

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-09-12 |
| Binds | lagent |
| Decision makers | nlink-jp maintainers |
| Triggered by | ベンチの `read-edit` タスクが 2/3、次いで 2/8 で「何も運ばない completion」により失敗し、生ストリームがその理由を示した |

## Context

ベースラインベンチ（ADR-0006）で `read-edit` タスクは 3 回中 2 回、
「the model returned no usable response (empty text, no tool call)」で
終わった。transcript には finish reason `stop`、出力 3〜4 トークン、
reasoning 1 トークンが記録されていた。トレース付き（`LAGENT_LLM_TRACE`）で
8 回反復すると 2 回再現し、どちらも `read_file` が修正対象のファイルを返した
直後で、生ストリームは毎回同じだった: `reasoning_content` が `<tool_call|>` の
delta 1 つ、空の delta 1 つ、`finish_reason: stop`、`completion_tokens: 4` の
usage。

モデルは壊れた開始トークンでツール呼び出しを始め、サーバはその迷子の
トークンを reasoning チャネルへ流し、生成は止まった。テキストにもツール
呼び出しチャネルにも何も届いていない。まったく同じリクエストを再送すると、
他の全反復では正常なツール呼び出しが出た — 不具合は 1 トークンのサンプリング
にあり、会話にはない。

今日のランタイムの答えは gem-agent のもの: 空応答を報告し、何も保存せず、
ターンをエラーで終える。対話中なら操作者が再送する。`-p` では実行はそこで
終わり、パイプラインは 2 度目のリクエストなら起きなかった障害のエラーを見る。

## Decision

空の completion — テキスト無し、ツール呼び出し無し、finish reason は問わない
— は同一リクエストで**多くて 2 回再送する**。履歴は変わっていない（何も保存
していない）ので、リクエストは失敗したものとバイト単位で同じで、サーバの
接頭辞キャッシュが数秒で答える。再送のたびに操作者に通知し（`OnNotice`）、
transcript は全試行を `assistant_empty` として記録する。再送したものには
`retried: true` が付く。3 度目の空 completion は従来どおり同じエラーと同じ
文言でターンを終える。

意図して有界: 再送は 2 回、ループにはしない。この記録を書いた時点の上限は
1 回で、障害は一度きりの誤サンプルだという読みに基づいていた。同じ日に
空が 2 回続く実行が出て、トレースしたリクエストをサーバに 4 回再生すると
2 回が空だった — 起きる地点では、障害は一度きりではなくコイン投げである。
再送 1 回では 4 分の 1 が取りこぼされ、2 回なら 8 分の 1 で、代価はキャッシュ
済みの数秒。同一リクエスト 3 回がすべて空なら操作者が見るべきである。再送は
他のモデル呼び出しと同様にターン予算のラウンドを 1 つ消費し、キャンセル
されたコンテキストでは再送しない。

## Consequences

- ベンチの `read-edit` 種別は支配的な失敗を失う。実測効果はベースラインの
  隣、`reference/bench.md` に記録する。
- one-shot パイプラインは、次のリクエストでは起きない障害で失敗しなくなる。
- `assistant_empty` レコードが `retried` を持つので、transcript はランタイム
  が再送したか、それが効いたかを語る。
- 空 completion のもう 1 つの形 — モデルが変更を実行せず「これから行う」と
  語って終わる — はこの記録の対象ではない。それは不具合ではなく計画で、
  続くプロンプト改訂のために計測する。

## Alternatives considered

- **ターンを失敗させたままにする。** 却下: 操作者の唯一の対処は同じ
  メッセージの再送で、それはランタイムにできることそのものであり、`-p` に
  操作者はいない。
- **何かが届くまで再送する。** 却下: 無限の再送は答えなくなったサーバを
  隠す。上限は計測した発生率から定めるのであって、外すのではない。
- **再送時にリクエストを変える**（促しメッセージ、別の seed）。不要:
  計測した最悪の地点でも同一リクエストの再送は半分成功し、同一リクエストは
  接頭辞キャッシュを保つ。促しは履歴の外に置く仕組みも要る。
- **迷子のトークンを reasoning に流さないようサーバに頼む。** 手が届か
  ない: 挙動は推論サーバとモデルのもので、ランタイムは結果しか見ない。
- **reasoning チャネルの `<tool_call|>` をツール呼び出しとして扱う。**
  却下: 回復すべき呼び出しが無い — 名前も引数も無い — し、制御のために
  reasoning チャネルを読むと、ランタイムの挙動がサーバ固有のトークン処理に
  依存する。
