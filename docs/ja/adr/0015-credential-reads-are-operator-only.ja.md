## 背景

ランタイムは資格情報の一覧を 1 つ、`internal/sandbox` に持つ: home
相対のディレクトリ（`.ssh`、`.aws`、`.config/gcloud`、`.config/mcp-bridge`
…）、home 相対のファイル（`.netrc`、`.git-credentials` …）、どこにあっても
秘密である名前（`.env` とその変種、`id_rsa` と他の秘密鍵、
`credentials.json`、サービスアカウントのファイル）、そしてコミットされる
テンプレート `.env.example`、`.env.sample`、`.env.template`、`.env.dist`
への再許可 1 つ。本記録までは 3 箇所で強制されていた:

- Seatbelt プロファイル: read レーンと write レーンは全項目への
  `file-read*` を拒む。operator レーンは拒まない — 資格情報を読むのは
  操作者の仕事だから（gem-agent ADR-0073）。
- 規則層、`write_file` と `edit_file` について: 資格情報のパスは Block。
- シェルの Block 床: それを名指すコマンドはどのレーンでも操作者に尋ねる。

read ツールはそのどれも参照していなかった。`read_file`、`search_files`、
`view_image`、`file_info` が検査するのはルート — プロジェクトとセッション
作業ディレクトリ、`os.Root` 経由 — だけで、それ以外は何も見ないので、
プロジェクト自身の `.env` への `read_file .env` は「read-only tool: Safe」
だった: どのモードでも尋ねずに走り、ファイルの内容はツール結果に、つまり
モデルのプロンプトの一部と transcript の 1 行になった。`search_files
API_KEY` は同じファイルの一致行を返した。レビューの第 10 章はこれを
放置させた混同を述べている: write ツールの資格情報パスに対する Block は
「ファイルツールは資格情報パスを拒む」と読めるが、そう読んではならない。

答えのためにランタイムが既に持っているもの:

- **操作者専用の Review**（gem-agent ADR-0072 §4）は常置の答えが決して
  出せない判定: セッション許可リスト、`"never"` ポリシー行、`--allow` の
  許可はそれに答えられず、`--auto` はエスカレートし、単発（`-p`）は
  尋ねる相手が居ないので拒否する。write ツールは後続セッションが信頼する
  ファイルに、シェルツールは operator レーンにそれを使う。`Agent.gated` は
  非変更の呼び出しの床判定を既にゲートへ送っている（read レーンで宣言
  された `sudo` が先例）ので、機構に新しい経路は要らない。
- **実パス。** write ツールの判定はツールが開く実パスで取られるので、
  `AGENTS.md` を指すリンク `notes.md` は `AGENTS.md` への書込である。
  `.env` を指すリンク `notes.txt` は読取における同じ穴。
- **全てのスキップは報告される**（gem-agent ADR-0052）: 列挙ツールは
  除いたもの — 無視ディレクトリ、大きすぎるファイル、上限で切った一覧 —
  を既に数え、角括弧の 1 行で、もっと見る方法とともに言う。

`@` 添付は操作者自身の入力で、どのゲートも通らずモデルに届く。モデルの
手が届く範囲ではなく、ここでの論点ではない。`load_skill` は発見済み
スキルディレクトリの中のファイルを尋ねずに読み（ADR-0011）、これも一覧の
外: スキルディレクトリは操作者自身が置いたもので内容でピン留めされ、
そこにある資格情報ファイルは操作者が置いたものである。一覧が名指さない
ファイルの内容も同様: `config.yaml` の中のトークンは他のファイルと同じく
読まれる。一覧は全ての強制点が共有する有限の名前の集合であって、検出器
ではない。

## 決定

1. **資格情報パスへの単一ファイル read ツールは操作者専用の Review。**
   `read_file`、`view_image`、`file_info`（バッチ形式はパスごとに —
   20 のうち 1 つが資格情報なら資格情報の読取）は、ツールが開く実パスに
   解決したパスが `sandbox.CredentialPath` に一致すれば `OperatorOnly` 付き
   Review: どのモードでも必ず尋ねる。セッション許可リスト、`"never"` 行、
   `--allow` はそれに答えず、`--auto` はエスカレートし、`-p` は拒否する。
   テンプレートの再許可はレーンと同じく適用され、`.env.example` は通常の
   ファイル。これはレーンを正確に写す — read レーンと write レーンは一覧を
   読めず、operator レーンは読め、operator レーンは操作者だけが承認する
   唯一の判定である。
2. **列挙ツールは飛ばして、飛ばしたと言う。決して尋ねない。**
   `search_files`、`list_files`、`list_tree` は一覧が名指す項目 — ファイル
   でもディレクトリでも、プロジェクト相対パスで判定 — を除き、他の全ての
   スキップと同じ形で件数と最大 5 つの名前を、経路 — そのうち 1 つへの
   `read_file` は操作者に尋ねる — とともに報告する。`.env` の中に無言で
   何も見つけない検索は偽陰性であり、言わずに `.env` を隠す一覧は偽の
   「無い」であり、走査中の資格情報ファイルごとのプロンプトはモデルが
   訊いていない十数個の質問になる。
3. **一覧は 1 つ、判定点は 1 つ。** `internal/sandbox` が一覧を持ち、
   プロファイル、write ツールの Block、シェルの床、read ツールの Review、
   列挙のスキップの全てがそれを読む。新しい資格情報の置き場所はそこに
   加え、他のどこにも加えない。判定は `Agent.decide` から `risk.Classify`
   — `internal/archtest` が固定する唯一の判定点 — で取る。`risk.PathJudged`
   は `decide` がパス引数を先に実パスへ解決するツールを名指すので、read
   ツールは write ツールとその一覧に同居し、2 つ目の一覧を生やさない。
4. **`@` 添付はそのまま。** 操作者がパスを打った。操作者がゲートである。

## 帰結

- ファイルツール経由では、プロジェクトの `.env` は操作者の yes があった
  時だけ、毎回、対話中にモデルへ届く。残るシェル経路 2 つは下の残余が
  名指す。無人実行は write レーンを拒まれるのと同じくそれを拒まれる
  — `.env` の内容を要する単発ワークフローには設計上の経路が無く、それは
  ADR-0010 が全ての Review 呼び出しについて述べる天井。単発の拒否は stderr
  に理由を名指し、モデルは常置の無人拒否文を受け取る。
- `search_files` の結果が資格情報ファイルの行を運ぶことは無く、フッタが
  飛ばしたファイル数と名前を言う。`list_tree` と `list_files` は除いた
  ものを言い、資格情報ファイルしか無いディレクトリは「空」ではなく
  フッタとして一覧される。
- `file_info` は内容を返さないが、資格情報ファイルには尋ねる: ハッシュは
  推測した秘密の照合器であり、規則はツールが返すものではなく開くパスに
  ついてのもの — 規則 1 つ、ツールごとの例外は考えない。
- ツールの説明がそれを言う — 経路（ADR-0008）。モデルは質問を予期し、
  床がまた尋ねるシェル経由で再試行しない。
- 規則層は read ツールのパス検査と `PathJudged` を得る。`Agent.decide` は
  パス判定ツール全てについて `path` と `paths` を解決する。`internal/tools`
  はスキップとそのフッタを得る。設定キーも設定行も無し: トグル付きの
  資格情報読取はバイパスである。
- DLP ではない: 一覧が名指さないファイルの中の秘密は、レビュー第 10 章の
  言うとおり他のファイルと同じく読まれる。不変。
- **残余 — 記録するが、ここでは閉じない**（本記録の独立レビュー、
  `sandbox-exec` 下で実測）。(1) read レーンは `~/.config/lagent/config.toml`
  — 環境変数ではなくファイルに置いた `[llm].api_key` を含む — と状態ルート下の
  transcript を読める。あるセッションで承認された `read_file .env` は、後の
  セッションの無承認の `cat` が返せる 1 行になる。どちらのパスも資格情報
  一覧に無い。閉じるには、read/write レーンで設定ファイルのパスと状態ルート
  下の `sessions/`・`memory/` を拒みつつ同じルート下の作業ディレクトリは
  書けるままにし、そもそもキーをファイルに置いてよいかを決める必要がある —
  独自の記録に値する。(2) write レーンは資格情報名の読取を拒むが改名は
  拒まない: 承認された write レーンのコマンド 1 つで `mv .env notes.txt &&
  cat notes.txt` は読めてしまい、その後の `read_file notes.txt` は通常の
  読取になる。テキストの床が捕まえるのは字面の `.env` で、`.en?` ではない。
  閉じるには write レーンで資格情報名への `file-write*` を拒むことになり、
  それは同レーンでの `cp .env.example .env` も止めるので、その代価を見た
  うえで決める。

## 検討した代替案

- **write ツールと同じ Block。** 却下: Block と操作者専用 Review はゲート
  では同じ床だが、記録とプロンプトで言うことが違う。資格情報ファイルへの
  書込はモデルがすべきことでは決してなく、読取は時に操作者がまさに望む
  こと — operator レーンはそのためにある — で、operator レーンが運ぶ
  判定が問いの正直な名前。
- **プロンプト無しで即拒否。** 却下: operator レーンの規則は操作者が
  決めること。承認され得ない read ツールはモデルをシェルへ向かわせ、
  床がどのみちその読取について尋ねる — 1 つの問いに 2 つのプロンプト。
- **read ツールでも飛ばす**（`read_file` が「skipped」を返す）。同じ理由で
  却下: 操作者が承認したはずの読取が不可能になる。
- **`search_files` で尋ねる。** 却下: 検索は走査で、資格情報ファイルごとの
  プロンプトはモデルが訊いていない多数の質問になる。走査は尋ねずに、
  内容は読まずに、が保たれるべきで、フッタ付きのスキップは両方を保つ。
- **実パスでなく綴りで判定。** 却下: write ツールは既に実名で判定する
  （`AGENTS.md` を指すリンク `notes.md`）。`.env` を指すリンク `notes.txt`
  は同じ穴。
- **内容を検査して秘密を検出。** 却下: 無限領域。一覧は有限で、文書化され、
  全ての強制点が共有する。検出器は独自の取りこぼしを持つ 2 つ目の規則に
  なる。
