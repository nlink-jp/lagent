# ADR-0006: Phase 2 がランタイムを変える前に、タスクベンチで計測する

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-09-12 |
| Binds | lagent |
| Decision makers | nlink-jp maintainers |
| Triggered by | Phase 1 の出口計測が比較にならなかった: 同じ指示に対して Gemini はツールループで作業し、ローカルモデルは 1 ラウンドで答えた。それがどのタスクで起きるのかをリポジトリの何も言えなかった |

## Context

RFP の Phase 2 一覧（compaction、自動承認のモデル層、skills / memory /
hooks、ローカル向けプロンプト改訂、thinking トグル）は「Phase 1 の計測
結果を根拠に」採否を決める。Phase 1 が生んだのは計測 1 つと観察 1 つ:
usage レコードは gem-usage-lens 互換であること、そして Gemma 4 がコーディング
タスクを 1 ラウンドで答えたこと。観察は一様ではない — 同じランタイムの
lookup セッションは MCP サーバを 6 つロードし、そのツールを 11 回呼んだ —
つまり一部のタスク種別の性質であって、境界は分かっていない。

Phase 2 の全項目がその境界に依存する。compaction とモデル層は多段ループを
前提にする。プロンプト改訂は「前」の数字が無ければ判定できない。thinking
トグルはトークンと引き換えに得る挙動を数えなければならない。再現可能な
計測が無ければ各項目は印象で決まる — 旧フォークがそう判定され廃棄された
のと同じ形になる。

今日ある計測手段: `-p` はタスクを無人で走らせる。transcript は全メッセージ、
ツール呼び出し、usage 行を記録する。Phase 1 の隔離 `HOME` E2E ハーネスは、
実行を操作者の設定から独立にできることを示した。gem-usage-lens は合わない:
`ingest` は操作者の実 store に書き、store の重複排除はセッションルートを
キーにし、そこで引かれる比較（費用）は Phase 1 がランタイム間では無意味と
示したものである。

## Decision

リポジトリ内の**タスクベンチ**。手で走らせ、固定タスク集に対するランタイムの
挙動を計測し、Phase 2 の ADR が根拠として要する表を出す。

1. **タスクはフィクスチャ。** `bench/tasks/<name>/` に `task.toml`
   （プロンプト、期待、必要なサーバ）と、実行ごとに新しいプロジェクトになる
   `fixture/` ディレクトリを置く。6 タスクで Phase 1 が挙げた種別を覆う:
   検索して答える、読んでから直す、3 ファイルにまたがる変更、数を出す
   シェルコマンド、MCP lookup、見るべき画像。期待は機械的 — ファイルが
   文字列を含む/含まない、回答がパターンに合う、ツール呼び出しが N 回以上 —
   なので「完了」はベンチが述べる事実であって判断ではない。
2. **構成は設定ファイル。** `bench/configs/<name>.toml` は完全な
   `config.toml` で、ベンチの実行は比較する構成を名指しする。プロンプト改訂、
   thinking トグル、ツール説明の変更は、同じタスクに対する構成 1 つ、または
   バイナリ 1 つ（`--bin`）の追加として計測する。
3. **実行は全て隔離。** ランナーは実行ごとに専用の `HOME`（設定、global
   `mcp.json`）、専用の状態ルート（`LAGENT_STATE_DIR`）、フィクスチャの
   新しい複製を与える。操作者の設定、セッション、プロジェクトは決して
   読まれず書かれない。ベンチ自身の stdio MCP サーバ（`bench/mcpfixture`）が
   lookup タスクに固定データで答えるので、MCP 種別にネットワークも操作者の
   サーバも要らない。
4. **ケースを外側、構成を内側、呼び出しごとにタイムアウト 1 つ。** 各タスク・
   各反復について構成を連続して走らせ、ローカルサーバの状態（キャッシュ、
   負荷）の揺れが全構成に等しく当たるようにする。各実行は自分の期限を持ち、
   進捗は実行が終わるたびに印字される。
5. **transcript が計測値。** 実行後、ベンチはランタイム自身のローダで
   セッション transcript を読み、数える: ラウンド数（ツール呼び出しを運ぶ
   assistant メッセージ）、ツール名ごとの呼び出し数、usage レコードの
   prompt / output / cached トークン、壁時計時間、終了コード、期待が成立
   したか。`bench report` は結果ディレクトリをタスク×構成の表 1 つに畳む:
   完了率、ラウンド数の中央値、ツール呼び出し数の中央値、prompt トークンの
   中央値、壁時計時間の中央値。
6. **参照ランタイムにも同じタスクを走らせる。** ランナーはランタイム
   プロファイル（バイナリのフラグ、状態ルート変数、transcript の配置）の
   有限表を持つ。gem-agent のプロファイルにより、各タスクの上限挙動が lagent
   の隣に数字として並ぶ — 費用が同じだと装うことなく。プロファイルは
   gem-agent のバイナリに対して検証してから加える。それより前には加えない。

ベンチはバイナリには何も出荷しない。`bench/` はモジュール内の独立した
`package main` で `go run ./bench` で走り、結果ディレクトリは git が無視する。
Phase 2 の ADR は判断の根拠にした表を引用する。

## Consequences

- 最初のベンチ実行が Phase 2-0 の成果物: ベースライン構成でどのタスク種別が
  1 ラウンドで終わるかの表。検証する 3 仮説は実行前に書き留める: system
  プロンプトに「まずリポジトリを見る」契機が無い。タスクが許せばモデルは
  事前知識でコーディングタスクに答える。thinking モードは計画を可視の
  本文の外へ移す。
- 以後の Phase 2 各項目は、実装前にこの表への期待効果を、実装後に実測効果を
  述べる。
- ベンチ 1 回はローカルサーバの実時間を食う（6 タスク × 3 反復 × 2 構成 =
  36 実行。cold の接頭辞は約 2 分）。ベンチは手で走らせ、`make check` には
  決して入れない。
- タスク集は小さく人工的。ランタイムが多段作業に入るかを測るのであって、
  コーディングの上手さを測るのではない。モデルがプロンプトだけで答えられる
  タスクはベンチに含めてはならず、フィクスチャは答えがファイルの中にしか
  無いように書く。

## Alternatives considered

- **gem-usage-lens で比較する。** 却下: 操作者の実 store に書き、セッション
  ルートをキーにし、測るのは費用で、それは Phase 1 がランタイム間で比較
  できないと示した。`verify --sessions-root` は今ある互換性検査のまま。
- **手動セッションを後から読む。** 却下: 再現不能、操作者の設定から隔離
  されず、それが生んだ唯一の観察こそ境界に変えられなかったものである。
- **`go test` のベンチマーク。** 却下: 実サーバに対する数分の実行はテスト
  スイートに属さず、バッファされたテスト出力は失速した実行を最後まで隠す
  （knowledge のベンチ項目）。
- **操作者の設定にある実 MCP サーバ。** フィクスチャとしては却下: 答えが
  変わり、ネットワークを要するものがあり、操作者の `mcp.json` に依存する
  ベンチは隔離されていない。単発なら操作者が構成でそれらを指すことはできる。
